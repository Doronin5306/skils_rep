# Tender Parser

Все парсеры портфеля решают одну задачу одинаково: раз в N часов собрать процедуры, опубликованные за день, положить их в файловый архив и отправить в общую БД через tenders-api. Этот скил фиксирует общую схему и грабли, на которые уже наступили — чтобы новый парсер не повторял инциденты старых.

## Что делать

- **Новая площадка** → весь «Процесс» ниже.
- **Доработка/починка существующего парсера** → сначала прочитай базу знаний проекта (`KNOWLEDGE.md` в корне или `kb/wiki/index.md` + `CLAUDE.md` у rts_tender), затем нужный раздел `references/`. Соседние проекты лежат в `/Users/b2b-connect/Doronin/<проект>` — сверяйся с ними, там уже решены похожие задачи.
- **«Почему не спарсена закупка N?»** → `references/gotchas.md`, раздел «Разбор пропуска».

Справка (читай по необходимости):

| Файл | Когда читать |
|---|---|
| `references/platforms.md` | Карточка каждого из 6 парсеров: площадка, вход, сбор, документы, деплой. Читай, чтобы найти ближайший образец под новую площадку. |

## Процесс (новая площадка)

### 1. Разведка — сначала самый дешёвый путь

Не начинай с Selenium. Проверяй по порядку и останавливайся на первом, что работает:

1. **JSON API** за страницей (вкладка Network): кабинет app.rts-tender.ru отдаёт поиск и модель процедуры JSON-ом (`gz_spb/rts_parser.py`).
2. **requests + cookie jar** по серверному HTML: rosatom (движок B2B-Center) целиком работает без браузера, даже вход — POST формы с CSRF.
3. **Selenium** — только если без браузера нельзя: SPA (Angular/Vue), JS-челлендж, вход по ЭЦП через плагин КриптоПро. Даже тогда можно войти браузером, а дальше перенести cookies в `requests.Session` (`rts_parser.Api`).

Что выяснить и записать с датой в `KNOWLEDGE.md` проекта (append-only журнал, проверенное отдельно от предположений):
- URL списка, фильтр по **дате публикации** (поля от/до), пагинация, шаг и предел глубины;
- нужен ли вход и для чего (часто список и карточки открыты, а документы — только после входа);
- вёрстка карточки: сколько видов (у utp_sberbank их 3), селекторы пар «подпись → значение»;
- где документы: на площадке, в ЕИС (zakupki.gov.ru), на сайте заказчика;
- лимит скорости: при каком темпе приходит 429/капча и как долго длится бан. Бан проверяй запросом **с cookie jar** — без кук редирект может не дойти до капчи и создать ложное «бан снят»;
- объём за день — от него зависит темп и расписание.

Разведку на продовой площадке делай малыми порциями (`--limit 3`, архив в `/tmp`, без отправки) — бан по IP бьёт по всем парсерам на этой машине.

### 2. Согласовать архитектуру с пользователем

Покажи итоги разведки и предложи: способ доступа (API / requests / Selenium), вход, где брать документы, раздельный ли режим файлов, где деплоить. Реализацию начинай после согласия, с маленького вертикального среза (один тип процедуры, десятки записей).

### 3. Каркас

Возьми `assets/parser_skeleton.py` (если нужен браузер — добавь фрагменты из `references/patterns.md`). Обязательные свойства, ради которых он так устроен:

- **CLI**: без аргументов — сегодня; `--date YYYY-MM-DD` — конкретный день (добор вчерашнего после полуночи); `--limit N` — отладка; `--files` — докачка файлов отдельным процессом; `--resend [--date|--since] [--dry-run]` — дозаливка архива в tenders-api без похода на площадку.
- **Архив** — главный результат: `/archive/selenium/<парсер>/<YYYY-MM-DD>/<item_id>/` c `index.html` (без `<script>`/`<noscript>`), `info.json`, документы в подпапке. Папка дня — по **дате публикации** с карточки, не по дате сбора. Признак «процедура собрана» — файл, который пишется **последним**.
- **tenders-api — best-effort**: сбой отправки не роняет сбор, карточка остаётся в архиве и досылается `--resend`.
- **Пустая карточка = ошибка**, а не успех: не сохранять и не помечать обработанной, следующий прогон попробует снова.
- Ненулевой код выхода при сбое прогона (`sys.exit(0 if ok else 1)`), иначе cron/docker видят «успех».

### 4. Тесты

Сохрани реальные страницы в `tests/fixtures/` (вычистив персональные данные) и тестируй разбор на них. HTTP и Selenium мокаются, тесты не ходят в сеть, не требуют `.env` (фиктивные переменные в `conftest.py` — шаблон в assets). Под каждый воркараунд — тест, который его фиксирует (пустой грид, фильтр не применился, капча, длинное имя файла).

### 5. Живой прогон и деплой

Прогон на целевой машине с `--limit 3` и `--out-dir`/архивом в `/tmp`, без отправки. Проверь на Linux: часть багов (длина имени файла в байтах, `maximize_window` под Xvfb) не проявляется на Windows/macOS. Затем деплой по `references/deploy.md`, ключ tenders-api — отдельный на platform, запрашивается у владельца parsers_orm.

### 6. Записать знание

После разведки, инцидента или фикса, меняющего поведение, — новая датированная запись в `KNOWLEDGE.md` (старые не переписывать: история находок важна). Если в проекте есть `raw/` + `wiki/` — веди её через скил llm-wiki.

## Границы

- **parsers_orm / tenders-api не трогать** — его ведёт другая сессия. Нужна новая platform, новое поле или изменение схемы → сформулируй промпт для владельца.
- Секреты (`.env`, ключи, пароли, строка `Upstream proxy:` из stdout с логином прокси) не попадают ни в git, ни в KNOWLEDGE.md, ни в ответы.
- В Postgres напрямую не писать — только через tenders-api.
