# Лучшие практики создания скилов

## Как Claude загружает скил (progressive disclosure)

1. **Метаданные** (`name` + `description`) — всегда в контексте, для всех скилов сразу. Поэтому description должен быть ёмким.
2. **Тело SKILL.md** — загружается, когда скил сработал. Держи < 500 строк.
3. **Ресурсы** (`references/`, `scripts/`, `assets/`) — читаются/запускаются только по необходимости. Скрипты можно выполнять, не загружая их текст в контекст.

## Поля frontmatter

| Поле | Обяз. | Назначение |
|---|---|---|
| `name` | да | kebab-case, ≤ 64 символа, совпадает с именем папки |
| `description` | да | что делает + когда использовать, ≤ 1024 символа |
| `allowed-tools` | нет | инструменты, разрешённые без запроса, пока скил активен (напр. `Bash(git:*), Read`) |
| `argument-hint` | нет | подсказка аргументов при вызове как `/skill-name …` |
| `disable-model-invocation` | нет | `true` — скил вызывается только вручную через `/skill-name`, Claude сам его не запускает. Для действий с побочными эффектами (деплой, отправка сообщений) |
| `model` | нет | модель для выполнения скила |

Используй только то, что действительно нужно. По умолчанию — `name` и `description`.

## Шаблоны description

Хороший:
```
Генерирует еженедельный отчёт по продажам из CSV-выгрузки CRM в формате xlsx
с графиками. Используй, когда пользователь просит отчёт по продажам, сводку за
неделю, разбор выгрузки CRM, или прикладывает файл sales_*.csv — даже если
слово «отчёт» не звучит.
```

Плохие:
- `Помогает с отчётами.` — непонятно что и когда, будет срабатывать случайно или никогда.
- `Скил для работы с данными, Excel, CSV, графиками, аналитикой, отчётами…` — простыня ключевых слов без сути, конфликтует с другими скилами.

## Паттерны структуры тела

**Рабочий процесс (workflow)** — нумерованные шаги, когда порядок важен:
```
## Процесс
1. Собери вход …
2. Запусти `scripts/x.py` …
3. Проверь …
```

**Выбор варианта** — когда скил покрывает несколько случаев:
```
## Что делать
- Новый файл → раздел «Создание»
- Правка существующего → раздел «Редактирование»
```
Для больших вариантов — отдельный файл на вариант в `references/` (напр. `references/aws.md`, `references/gcp.md`), Claude прочитает только нужный.

**Формат вывода** — если результат должен быть строго определённым, дай шаблон:
```
## Формат отчёта
# <Заголовок>
## Итог
## Детали
```

**Примеры** — пара «вход → выход» лучше абзаца объяснений.

## Когда что класть в подпапки

| Признак | Куда |
|---|---|
| Claude каждый раз пишет один и тот же код | `scripts/` |
| Шаг должен быть детерминированным (парсинг, валидация, генерация) | `scripts/` |
| Справка > ~100 строк, нужна не всегда (API, схемы, политики) | `references/` |
| Файл копируется в результат (шаблон, логотип, boilerplate) | `assets/` |

Для `references/` длиннее ~300 строк добавь оглавление в начале. В SKILL.md всегда пиши, *когда* читать конкретный файл.

## Скрипты

- Без интерактивного ввода, параметры — аргументами.
- Понятные сообщения об ошибках и ненулевой код выхода.
- Только стандартная библиотека, если можно; иначе — опиши зависимости в SKILL.md.
- Python здесь — 3.9 (системный macOS): без `match`, без `X | Y` в аннотациях.
- Сделай исполняемыми: `chmod +x`.

## Анти-паттерны

- **Объяснять очевидное.** Claude знает, как писать Python и пользоваться git. Пиши только специфику.
- **ВСЁ КАПСОМ / MUST / НИКОГДА** без объяснения причины. Модель начинает перестраховываться в неожиданных местах.
- **Переобучение на одном примере.** Инструкции должны обобщаться на похожие запросы, а не описывать единственный случай из разговора.
- **Дублирование** между SKILL.md и references — расходится при правках.
- **Секреты в скиле** (токены, пароли). Ссылайся на переменные окружения.
- **README/CHANGELOG внутри папки скила** — лишнее; всё нужное — в SKILL.md.
- **Захардкоженные абсолютные пути в скриптах** — вычисляй пути относительно `__file__`.
