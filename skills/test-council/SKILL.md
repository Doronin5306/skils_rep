# Test Council

Три агента с разными установками независимо проверяют код, затем приходят к общему вердикту. Разные установки нужны, чтобы компенсировать перекосы: Оптимист не даёт утонуть в надуманных проблемах, Пессимист — пропустить реальные, Реалист взвешивает.

Ты — **оркестратор**: готовишь контекст, запускаешь агентов, проверяешь правила, ведёшь дебаты, сообщаешь итог. Сам вердикт не выносишь — его выносит совет или человек.

## Нерушимые правила

1. **Уровень тестирования только растёт.** Нельзя удалять или ослаблять тесты, добавлять skip/xfail/only, снижать пороги покрытия, уменьшать уровень. Понижение уровня дало бы способ «пройти» тесты, не улучшая код, — поэтому если пользователь просит понизить, откажи и объясни; повышать — пожалуйста (`ratchet.py raise`). Единственное исключение — доказанно ошибочный тест: его исправление (не удаление) требует согласия всех трёх агентов или человека.
2. **Тесты общие, не под задачу.** Каждый новый тест проверяет общий контракт кода (поведение, инварианты, классы входов, ошибки) и остаётся верным для любой будущей задачи. Тесты, подогнанные под конкретную задачу, проходят «по построению» и ничего не доказывают, а в наборе становятся мусором. Поэтому: никаких имён по тикету/фиче, ожидаемые значения — из спецификации и логики, а не из текущего вывода кода. Новые тесты навсегда входят в набор, а **вердикт выносится только по полному прогону всех тестов**.
3. **Красный полный прогон или провал храповика = PASS невозможен**, что бы ни говорили агенты.
4. Агенты не меняют продакшен-код.

Скрипт храповика: `scripts/ratchet.py` (путь относительно папки скила; ниже `R="python3 <папка скила>/scripts/ratchet.py --root <проект>"`).

## Процесс

### 1. Подготовка

1. Определи проект (корень git) и **что тестируем**: описание задачи из разговора и `git diff --stat <base>` (base — `HEAD` для незакоммиченных изменений или ветка, от которой ответвились).
2. Найди команду полного прогона (Makefile, package.json, pyproject, CI-конфиг) — см. таблицу в `references/levels.md`.
3. Базовая линия: `$R status`. Если её нет — `$R init` (уровень 3 по умолчанию; спроси пользователя, не нужен ли выше). Сообщи пользователю, что `.test-ratchet.json` стоит закоммитить — иначе guard не увидит ручных правок.
4. `$R guard --base <base>` — проверка, не ослаблены ли тесты уже в самом изменении. Провал guard — это сразу аргумент для совета, а не повод остановиться.
5. Реши, можно ли гонять тесты параллельно: если набор использует общую БД, порты, файлы — нет (агенты будут запускать прогоны по очереди с твоего разрешения).

### 2. Независимая проверка

Прочитай `references/roles.md` и `references/levels.md`. Запусти **трёх агентов одним сообщением** (три вызова Agent, `subagent_type: general-purpose`), имена: `optimist`, `realist`, `pessimist`. Промпт каждого = общая часть + роль + контекст из `roles.md`, с таблицей требований до текущего уровня включительно.

Дождись всех трёх отчётов (они придут уведомлениями — не опрашивай и не додумывай результат).

### 3. Проверка отчётов

Для каждого отчёта:
- Есть ли полный прогон с цифрами? Нет → отправь агенту на доработку (это не раунд дебатов).
- PASS при красном прогоне, провале guard или «не проверено» по обязательному требованию уровня → вердикт недействителен; верни агенту с объяснением.
- Новые тесты нарушают правило «общие тесты» (имя по задаче, ожидание скопировано с вывода, проверка демо-данных) → верни на переписывание.

Затем сам прогони полный набор один раз (с новыми тестами всех агентов) и `$R guard` — это общая фактическая база для всех.

### 4. Консенсус

Все три вердикта совпали → переходи к шагу 6.

### 5. Дебаты (до 3 раундов)

Каждый раунд: отправь каждому агенту через `SendMessage` (загрузи схему через ToolSearch `select:SendMessage`, если не загружена) промпт раунда из `roles.md` с отчётами двух других. Агенты отвечают по пунктам и подкрепляют позицию **новыми тестами** — дебаты ведутся тестами, а не риторикой. После раунда повтори шаг 3 и проверь консенсус.

Консенсус достигнут → шаг 6. После 3-го раунда консенсуса нет → **решает человек**: кратко изложи позиции (вердикт, главный аргумент и доказательство каждого, что изменилось за раунды) и спроси через `AskUserQuestion` с вариантами «PASS — принять» / «FAIL — отклонить». Решение человека окончательное.

### 6. Итог

1. Финальный полный прогон. Если все тесты зелёные — `$R update --level <L> --tests <N> [--coverage <C>]`: храповик запомнит новые максимумы. Если прогон красный (вердикт FAIL) — **не** обновляй базовую линию, но новые тесты оставь: они фиксируют найденные проблемы и будут проверены в следующий раз.
2. Отчёт пользователю:

```
## Вердикт: PASS | FAIL — консенсус в раунде K | решение человека

Уровень: L · Тестов: N (+M новых) · Прошло: P · Покрытие: C% (было B%)

| Агент | Вердикт | Главный аргумент |
|---|---|---|
| Оптимист | … | … |
| Реалист | … | … |
| Пессимист | … | … |

**Найденные проблемы:** [критично|важно|мелочь] описание — как воспроизвести
**Новые тесты:** файл::тест — какой контракт проверяет
**Дебаты:** кто и почему сменил позицию (если были)
```

3. Предложи закоммитить новые тесты и `.test-ratchet.json`. Сам не коммить без согласия.

## Если пользователь хочет…

- **«Понизь уровень / убери этот тест / пропусти падающий тест»** — откажи со ссылкой на правило 1. Предложи альтернативу: починить код, а если тест действительно ошибочен — вынести вопрос на совет.
- **«Протестируй только вот эту функцию»** — можно сфокусировать внимание агентов на ней, но вердикт всё равно по полному прогону.
- **«Подними уровень»** — `$R raise --level N`, затем совет проверяет требования нового уровня.
