# LLM Wiki (по Карпати)

Идея: вместо того чтобы каждый раз искать ответ в сырых документах (RAG), Claude один раз «компилирует» знания из источников в постоянную вики из связанных markdown-страниц и поддерживает её в актуальном виде. Вики — накапливающийся артефакт: каждый новый источник и каждый хороший ответ делают её богаче.

Разделение ролей: **человек** отбирает источники и задаёт вопросы; **Claude** пишет и поддерживает вики — резюме, перекрёстные ссылки, индекс, разрешение противоречий. Люди бросают вики, потому что поддержка дорогая; для Claude она почти бесплатна — поэтому не экономь на обновлении связанных страниц.

## Устройство базы

```
<kb>/
├── CLAUDE.md          # схема: соглашения этой базы (её дорабатывают вместе с пользователем)
├── raw/               # сырые источники — НЕИЗМЕНЯЕМЫЕ
│   └── assets/        # картинки и вложения
└── wiki/              # пишет только Claude
    ├── index.md       # каталог всех страниц: ссылка + одна строка
    ├── log.md         # хронологический журнал, только дописывается
    ├── overview.md    # обзор всей области знаний
    ├── sources/       # одна страница-резюме на каждый источник
    ├── entities/      # люди, компании, продукты, проекты
    ├── concepts/      # идеи, термины, методы
    └── syntheses/     # сравнения, анализы, сохранённые ответы
```

`raw/` не меняй никогда: это первоисточник, по которому всегда можно перепроверить или перекомпилировать вики. Если источник нужно поправить — попроси пользователя или положи новую версию рядом.

**Перед любой операцией** прочитай `<kb>/CLAUDE.md` (там могут быть особые правила этой базы) и `wiki/index.md`. Если базы ещё нет — начни с «Создание».

Форматы страниц, frontmatter и правила ссылок — в `references/page-formats.md`. Прочитай его перед первым созданием или правкой страниц в сессии.

## Создание базы

1. Уточни у пользователя путь и тему базы, если они не ясны из разговора.
2. Запусти:
   ```bash
   python3 scripts/init_wiki.py <путь> --topic "Тема базы"
   ```
   (путь к скрипту — относительно папки этого скила). Скрипт создаёт структуру, `CLAUDE.md`, `index.md`, `log.md`, `overview.md` и ничего не перезаписывает.
3. Предложи `git init` в папке базы — история версий защищает от неудачных правок. Предложи открыть папку как Obsidian vault (граф связей помогает видеть хабы и сирот).

## Ingest — добавление источника

Источник может прийти файлом, ссылкой или текстом в чате.

1. **Сохрани в `raw/`.** Ссылку — скачай и сконвертируй в markdown (`raw/YYYY-MM-DD-slug.md`, в начале — URL и дата). Текст из чата — сохрани так же. Картинки, важные для понимания, — в `raw/assets/`. Файл, уже лежащий в `raw/`, не трогай.
2. **Прочитай источник целиком** и обсуди с пользователем 3–5 ключевых выводов: что нового, что противоречит уже известному, на что обратить внимание. Если пользователь просил «просто добавь» — пропусти обсуждение, но выводы всё равно сформулируй в странице.
3. **Создай страницу источника** `wiki/sources/<slug>.md`.
4. **Обнови связанную вики** — это главная ценность. Пройди по сущностям и концептам из источника:
   - есть страница → допиши новые факты со ссылкой на источник, поправь устаревшее;
   - нет страницы, а тема значимая (скорее всего всплывёт снова) → создай;
   - новый факт противоречит существующему → не затирай: отметь противоречие на странице (раздел «Противоречия»), укажи оба источника.
   Один источник обычно затрагивает 5–15 страниц. Если затронул 1–2 — проверь, не упустил ли связи.
5. **Обнови `overview.md`**, если источник меняет общую картину.
6. **Обнови `index.md`** — каждая новая страница должна попасть в каталог.
7. **Допиши в `log.md`**:
   ```
   ## [2026-04-02] ingest | Название источника
   - создано: [[a]], [[b]]
   - обновлено: [[c]], [[d]]
   - противоречия: …
   ```
8. Коротко отчитайся пользователю: что создано/обновлено, найденные противоречия.

Добавляй источники **по одному** — так каждый получает полноценную интеграцию. Если пользователь дал пачку, обработай их последовательно, каждый — полным циклом.

## Query — ответ на вопрос

1. Прочитай `index.md`, выбери релевантные страницы, прочитай их; иди по `[[ссылкам]]` дальше, если нужно. На больших базах помогает `grep -ril "термин" wiki/`.
2. Отвечай по вики, а не по своим общим знаниям, и **ссылайся на страницы** `[[...]]`. Если в вики ответа нет или он неполон — так и скажи, а общие знания явно помечай как не из базы. Предложи источники, которые стоит добавить.
3. В `raw/` заглядывай, только если нужна точная цитата или вики явно неполна.
4. Если ответ ценный (сравнение, анализ, новая связь) — предложи сохранить его в `wiki/syntheses/` и обнови index и log (`## [дата] query | Вопрос`). Так исследование накапливается в базе, а не теряется в чате.

Ответ может быть не только текстом: таблица-сравнение, слайды Marp, диаграмма Mermaid — если так понятнее.

## Lint — проверка здоровья базы

Запускай по просьбе пользователя или предлагай после каждых ~10 ингестов.

1. Структурная проверка скриптом:
   ```bash
   python3 scripts/lint_wiki.py <путь>
   ```
   Находит битые ссылки, страницы-сироты, страницы вне индекса, источники из `raw/` без страницы в `sources/`, ошибки frontmatter.
2. Смысловая проверка — прочитай вики и ищи сам:
   - противоречия между страницами;
   - устаревшие утверждения, опровергнутые более новыми источниками;
   - концепты, которые упоминаются на многих страницах, но не имеют своей;
   - недостающие перекрёстные ссылки;
   - пробелы в знаниях — какие источники стоило бы найти.
3. Покажи пользователю отчёт, исправь очевидное (ссылки, индекс), спорное — обсуди.
4. Запиши в log: `## [дата] lint | N проблем, исправлено M`.

## Схема `CLAUDE.md`

Файл в корне базы — её «конституция»: тема, особые соглашения, категории, язык. Когда пользователь вводит новое правило («всегда указывай год публикации», «заведи раздел для рецептов») — добавь его в `CLAUDE.md`, чтобы оно действовало и в будущих сессиях.
