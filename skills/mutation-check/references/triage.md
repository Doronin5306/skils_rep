# Разбор непойманного мутанта

Читай, когда в выводе `mutate.py` есть вердикт кроме `KILLED`. Порядок: прибор → мутант → тест → правка. Каждый шаг заканчивается доказательством, а не мнением.

## 1. Прибор

Признаки, что врёт измеритель, а не код:

- `NO_TESTS` или в строке «Контроль» стоит 0 — цели не собрались. Типичные причины: опечатка в пути, неверный `cwd`, тесты уходят в `skip` без окружения (нет локального Postgres, нет `bsdtar`, не задана переменная). Смотри skipped в контрольном прогоне.
- `WRONG_TEST` на очевидном мутанте — перепрогнать `--only <id>`. Повторилось — значит, ожидаемый тест действительно не видит правку, переходи к шагу 3.
- Прогон после отката красный — откат не доехал или тесты нестабильны. Пока это не исправлено, ни одному вердикту не верить.
- Контроль исправности прибора (если результаты странные целиком): добавь заведомо «смертельный» мутант — например, функция возвращает константу. Он обязан дать `KILLED`, иначе неисправен прибор.

## 2. Пустой мутант

Мутант пуст, если мутированный код ведёт себя так же, как исходный, на всех входах. Чаще всего бывает, когда:

- **Удалён ранний выход, но не последующее употребление.** Пример (урок 22.09): убрали `if (at === undefined) continue`, но ниже `now - at` дал `NaN`, `NaN >= 1` → `false`, и лот пропускался так же, как с проверкой. Мутант-«без защиты» должен был быть `now - (at ?? 0)`. В Python аналоги: `None` → `TypeError`, пойманный общим `except`; пустая строка, которая отсеивается следующим фильтром.
- **Замена на эквивалент.** `x + 0`, `or None` для уже ложного значения, перестановка независимых строк.
- **Мутант задел ветку, которую тестовые входы не проходят**, и при этом никакой вход в принципе не доходит до неё (мёртвый код).

Доказательство непустоты: конкретный вход и два вывода — на исходном коде и на мутанте, разные. Не находится и мутант — не полное снятие правки → перепиши мутант (лучше через `revert` по коммиту правки) и перепрогони.

## 3. Слабый тест

Есть вход, на котором мутант ведёт себя иначе, а ожидаемый тест не падает. Значит, тест не наблюдает эффект правки. Типичные причины:

- фикстура не различает исходы (оба кода дают одинаковый результат на данных теста);
- `assert` внутри подменённой зависимости глушится `except Exception` проверяемого кода — собирать факты в журнал вызовов и утверждать ПОСЛЕ вызова;
- проверяется не тот признак (длина вместо содержимого, факт вызова вместо аргументов);
- тест на порядок проходит, потому что ожидаемый порядок совпадает с порядком по умолчанию.

Починка: добавить в тест именно тот вход из доказательства, где поведение различается. Критерий готовности — тест красный на мутанте и зелёный на коде с правкой (перепрогнать мутант). Не трогать сам мутант, чтобы тест «прошёл».

## 4. Правка-пустышка

Мутант — точное снятие правки, а входа, на котором поведение различается, нет. У правки нет наблюдаемого эффекта.

- **Снять правку** (откатить коммит или участок). Не писать тест, который её «поймает»: такой тест закрепляет иллюзию, что код что-то делает.
- Если исходное требование было в задаче — сообщить, что посылка не подтвердилась замером, и как это показано. Требование в задаче — тоже гипотеза (урок 27.08: React и без правки переиспользовал тот же узел).
- Если фактическое поведение важно — закрепить его отдельным тестом и доказать этот тест своим мутантом.

## Как отличить 2 от 4

| Вопрос | Пустой мутант | Правка-пустышка |
|---|---|---|
| Мутант = вся правка целиком? | нет, часть или неточная замена | да (`revert` по коммиту правки) |
| Что меняем | мутант | код (снимаем правку) |
| Тест | не трогаем | не подгоняем |

Если сомневаешься — построй мутант через `revert` и прогони заново: результат на точном снятии правки решает вопрос.

## Не pytest (jest, vitest, go test)

Скрипт рассчитан на pytest. Порядок для других раннеров тот же, вручную:

1. Контрольный прогон целей без мутации: число тестов > 0, всё зелёное, ожидаемый тест есть в выводе.
2. Цели задавать **шаблоном имени**, а не путём: позиционный аргумент jest — регулярное выражение, и `app/(tabs)/…` молча не совпадёт ни с чем (урок 23.09). Для отбора теста — `-t '<имя теста>'`.
3. Кэш трансформаций: `jest --no-cache` (или `--cacheDirectory=$(mktemp -d)`) на каждый прогон.
4. Сверять имя упавшего теста, вернуть файл (`git checkout -- <file>`), прогон после отката — зелёный.
