# Mutation Check

Правка существует, только если её снятие роняет тест, написанный под неё. Скил превращает это в замер: по мутанту на каждую проверяемую правку, вердикт выдаёт `scripts/mutate.py`, а не мнение.

Источник практики — `digitender-platform/.claude`: `roles/developer.md` шаг 4, `rules/corrections.md` правило 2, уроки 27.08, 22.09, 23.09, 24.10. Там лежат исходные случаи, если нужны подробности.

## Почему именно так

- **Мутант — код БЕЗ правки**, а не любая замена оператора. Мы проверяем не «тесты вообще», а то, что конкретная правка имеет наблюдаемый эффект и он закреплён тестом.
- **Падение должно быть тем самым тестом.** Если упал соседний тест, правку он не доказывает. Часто так проявляется прежний байткод (урок 24.10, PR #849: упал `test_bid_security_not_object` вместо `test_etp_fee_not_object`).
- **Свежий `PYTHONPYCACHEPREFIX` на каждый прогон.** `.pyc` считается годным по `mtime` с точностью до секунды и по размеру. Мутант той же длины (`540`→`600`, `<`→`>`), записанный в ту же секунду, исполнит прежний код. `PYTHONDONTWRITEBYTECODE=1` от этого не спасает: уже записанный `.pyc` всё равно прочтётся.
- **Контрольный прогон до мутаций.** Прогон, который не запустил ни одного теста, выглядит как «мутация выжила» (урок 23.09).
- **Только закоммиченный код.** Тогда откат проверяем (`git status` чист), а мутант через `--revert SHA` точно совпадает с правкой.

## Процесс

### 1. Опись правок

Для каждой проверяемой правки — строка: *что меняет в поведении → какой тест её закрепляет (имя) → мутант = код без неё*. Правка без своего теста — сначала тест (тест первым: он должен краснеть на коде без правки). Одна правка — минимум один мутант. В правке из нескольких независимых частей — мутант на каждую часть.

Правило формулировки мутанта (урок 22.09): «код без этой защиты», а не «строка заменена на строку». Удаляешь ранний выход (`return`, `continue`, `raise`) или проверку — убедись, что последующие употребления переменной тоже работают без защиты. Иначе защита уцелеет в виде `NaN`, `None` или исключения ниже по коду.

### 2. Закоммить и составь спеку

Закоммить правку и тесты. Спека — JSON рядом с работой (не коммить её в проект, лучше положить в scratchpad):

```json
{
  "cmd": "uv run pytest",
  "cwd": "backend/push-service",
  "env": {"TEST_OWN_PG_DSN": "postgresql://postgres:postgres@localhost:5432/push"},
  "mutants": [
    {"id": "timeout-default",
     "why": "правка: дефолт таймаута 540",
     "path": "app/config.py",
     "revert": "f16ecec4",
     "expect": ["test_express_timeout_default"],
     "tests": ["tests/test_config.py"]},
    {"id": "fee-not-object",
     "path": "app/parse.py",
     "replace": ["if not isinstance(fee, dict):\n        return None\n", ""],
     "expect": ["test_etp_fee_not_object"],
     "tests": ["tests/test_parse.py"]}
  ]
}
```

- Мутант задаётся одним из способов: `revert` (откат коммита правки по этому файлу — лучший вариант: ровно «код без правки»), `replace` `[старое, новое]` (старое встречается в файле ровно один раз), `patch` (путь к diff).
- `expect` — имя теста (`test_x`), `Class::test_x` или полный nodeid. Параметризованные `test_x[...]` сопоставляются по базовому имени.
- `tests` — цели pytest. Бери файл или модуль, где лежит ожидаемый тест, а не весь набор: так быстрее, и видно, что ещё задевает мутант.
- Пути в спеке — относительно `cwd`, а `cwd` — относительно самой спеки.

Один мутант можно прогнать без спеки:

```bash
python3 ~/.claude/skills/mutation-check/scripts/mutate.py --cwd backend/push-service \
  --cmd "uv run pytest" --path app/config.py --revert f16ecec4 \
  --expect test_express_timeout_default --tests tests/test_config.py
```

### 3. Прогони

```bash
python3 ~/.claude/skills/mutation-check/scripts/mutate.py spec.json --json-out mutants.json
```

Скрипт для каждого мутанта: контроль на чистом коде (тестов > 0, всё зелёное, ожидаемый тест среди прошедших) → мутант → проверка, что файл изменился → прогон со свежим кэшем → сверка имени упавшего теста → возврат файла байт-в-байт. В конце — прогон после отката, он обязан быть зелёным. Код возврата `0` — только если все мутанты `KILLED` и откат зелёный.

Тесты не на pytest (jest, vitest) — скрипт не подходит, порядок тот же, но вручную: см. `references/triage.md`, раздел «Не pytest».

### 4. Прочитай вердикты

| Вердикт | Что значит | Что делать |
|---|---|---|
| `KILLED` | упал ожидаемый тест | правка доказана |
| `WRONG_TEST` | упали другие тесты, ожидаемый — нет | не доказано: перепрогнать; если повторится — ожидаемый тест не мерит правку → разбор |
| `SURVIVED` | ничего не упало | разбор (шаг 5) |
| `BROKEN_MUTANT` | мутант ломает импорт или сбор тестов | переписать мутант: нужен работающий код без правки, а не синтаксическая ошибка |
| `EMPTY_DIFF` | мутант не изменил файл | переписать мутант |
| `NO_TESTS` / `CONTROL_RED` | прибор неисправен: тесты не запустились, красные на чистом коде или ожидаемого теста нет среди прошедших (опечатка в имени, тест не собирается) | чинить прибор, мутации не трогать |
| `APPLY_FAILED` | строка не найдена или патч не лёг | поправить спеку; для `revert` после поздних коммитов использовать `replace` |

### 5. Разбор непойманного — строго по порядку

Выжившую мутацию первой подозревают в неисправности прибора, потом сам мутант, и только затем тест или правку. Обратный порядок ведёт к правке исправного теста или к подгонке теста под несуществующий дефект.

1. **Прибор.** Контроль зелёный и тестов > 0? Цели те? Перепрогнать этот мутант (`--only <id>`). Кэш свежий уже гарантирован скриптом.
2. **Пустой мутант.** Докажи, что мутант меняет поведение хотя бы на одном входе: найди вход и выполни мутированный код на нём (REPL или одноразовый скрипт). Не находится, а мутант — не полное снятие правки (защита уцелела ниже по коду) → переписать мутант.
3. **Слабый тест.** Вход, где мутант ведёт себя иначе, найден, а тест его не видит → усилить тест именно на этом входе. Новый тест обязан падать на мутанте и проходить на коде с правкой — перепрогнать.
4. **Правка-пустышка.** Мутант — ровно снятие правки (`revert`), и ни на одном входе поведение не отличается → у правки нет наблюдаемого эффекта. **Снять правку**, а не изобретать тест, который её «поймает»: подогнанный под no-op тест хуже отсутствия теста, он закрепляет иллюзию. Если нужно, закрепить фактическое поведение отдельным тестом и доказать его своей мутацией (урок 27.08).

Отличить 2 от 4 можно вопросом: «мутант — это вся правка целиком или её часть?». Подробные признаки и примеры — в `references/triage.md`. Читай его, когда есть хоть один вердикт кроме `KILLED`.

### 6. Отчёт

В отчёт (описание PR, ответ пользователю) — таблица из вывода скрипта и строки контроля:

```
## Мутации
| id | правка | мутант | ожидаемый тест | упал | вердикт |
|---|---|---|---|---|---|
| timeout-default | дефолт 540 | revert f16ecec4 | test_express_timeout_default | test_express_timeout_default | KILLED |

Контроль на чистом коде: tests/test_config.py — 12 тестов, зелёный.
Прогон после отката: зелёный. Кэш байткода: свежий PYTHONPYCACHEPREFIX на каждый прогон.
Разбор непойманных: <id> — <прибор | пустой мутант → переписан | слабый тест → усилен | правка снята> — <чем доказано>.
```

Вердикт `KILLED` без совпадения имени не засчитывается. Снятую правку назови в отчёте явно: это результат, а не провал.
