# Интервью для составления плана

Цель — собрать достаточно, чтобы каждая задача в плане была выполнима **без** возврата к пользователю: кодер и тестировщики работают по тексту задачи, не по разговору.

Спрашивай раундами через `AskUserQuestion` (до 4 вопросов за раз, с вариантами ответа и рекомендацией первым пунктом). Сначала посмотри код (README, структуру, стек, тесты, CI, открытые issues) и не спрашивай то, что видно из репозитория. После каждого раунда коротко пересказывай понятое — так пользователь ловит недопонимание рано.

## Раунд 1 — Цель и рамки
- Что должно получиться в итоге? Для кого (пользователи, сценарии)?
- Что точно **не** входит (non-goals)?
- Есть ли сроки, приоритеты, внешние ограничения (бюджет, совместимость, лицензии)?
- Это новый проект или доработка существующего?

## Раунд 2 — Функциональность
- Ключевые сценарии / фичи — списком. Какие обязательны для первой версии?
- Входные и выходные данные, форматы, API, интеграции с внешними сервисами.
- Обработка ошибок и граничных случаев, важных для бизнеса.
- Роли и права доступа (если применимо).

## Раунд 3 — Техника
- Стек, версии, фреймворки (если не видно из кода) — или свобода выбора?
- Архитектурные ограничения: где хранить данные, как деплоить, производительность.
- Безопасность: секреты, персональные данные, аутентификация.
- Стиль кода, линтеры, соглашения о коммитах.

## Раунд 4 — Качество и процесс
- Уровень тестирования (1–5, см. скил test-council; по умолчанию 3). Напомни: понизить потом нельзя.
- Куда открывать MR (main? другая базовая ветка?), кто ревьюит и мержит.
- Путь к базе знаний для llm-wiki-сессии (существующая или создать новую).
- Нужно ли что-то согласовывать с пользователем по ходу (UX, публичные API)?

## Добивка
Если ответы открыли новые неясности — ещё раунд. Остановись, когда можешь написать для каждой задачи проверяемые критерии приёмки.

## Как нарезать задачи

- Одна задача = один MR, который можно независимо протестировать и смержить. Ориентир: от нескольких часов до дня работы.
- Сначала фундамент (структура, конфиги, CI, базовые модели), потом фичи.
- Зависимости — явно в `depends`. Чем меньше цепочки, тем больше задач можно делать без ожидания мержа.
- Критерии приёмки — проверяемые утверждения о поведении («POST /users с пустым email → 422»), а не «сделать хорошо».
- Название задачи — короткое и предметное: из него получается имя ветки.

Готовый план покажи пользователю целиком и правь, пока он не скажет «ок». Затем `plan.py validate`.
