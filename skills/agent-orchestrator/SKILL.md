# Agent Orchestrator

Эта сессия становится **контроллером**: держит план, раздаёт задачи пяти сессиям-воркерам, проверяет правила и ведёт задачу по конвейеру. Сам контроллер код не пишет и тесты не выносит — он координирует и следит, чтобы ни один шаг не был пропущен.

Если ты получил сообщение `[ORCH] …` — ты **воркер**: сразу переходи к разделу «Воркеры».

## Нерушимые правила

1. **В main (и master) не пушить никогда** — ни контроллеру, ни воркерам. Каждая задача — своя ветка `<id>-<название>`, результат попадает в main только через MR, который мержит человек. Это даёт человеку контроль над тем, что попадает в основную ветку. Правило подкреплено pre-push хуком (`scripts/install_push_guard.sh`); обходить хук (`--no-verify`) нельзя.
2. **Сначала тесты, потом MR.** MR открывается только после PASS совета тестирования (консенсус или решение человека).
3. **БЗ пополняется после MR** — каждая задача оставляет след в базе знаний.
4. Правила test-council действуют полностью: уровень тестирования только растёт, тесты общие, вердикт по полному прогону.
5. Не проси воркера сделать то, что запрещено или заблокировано в твоей сессии, — это обход решений пользователя о правах. Такое — к человеку.

Скрипты (пути относительно папки скила): `scripts/plan.py` — работа с планом, `scripts/install_push_guard.sh` — запрет пуша в main. Скрипт храповика — из скила test-council: `~/.claude/skills/test-council/scripts/ratchet.py`.

## Контроллер

### 1. План

Найди в корне проекта `ROADMAP.md` или `tasks.md` (также `docs/`).

- **Есть `tasks.md` в формате плана** (`## T1: …` + `- status:`) → `python3 scripts/plan.py --file <путь> validate`, затем `list`.
- **Есть `ROADMAP.md` или план в другом формате** → не переписывай его. Предложи пользователю сделать из него `tasks.md` в формате плана (с ссылкой на исходный roadmap) — это нужно, чтобы статусы и ветки вели скрипты, а не память. Без согласия — веди статусы вручную в `.orchestrator/state.md`.
- **Плана нет** → проведи интервью по `references/interview.md` — спрашивай максимально подробно, план должен быть понятен воркерам без разговора. Затем создай `tasks.md` из `assets/tasks.template.md`, покажи пользователю, правь до «ок», `plan.py validate`.

Новый или изменённый `tasks.md` в main не коммить напрямую: он попадёт в репозиторий вместе с первой задачей (кодер закоммитит его в ветку T1) или отдельным MR — спроси пользователя.

### 2. Подготовка репозитория

```bash
git -C <проект> fetch origin
bash scripts/install_push_guard.sh <проект>
git -C <проект> remote get-url origin        # github → gh, gitlab → glab
gh auth status   # или glab auth status
```
Проверь, что ты сам на базовой ветке без незакоммиченных изменений чужого кода (план — можно). Запиши `.orchestrator/` в `.git/info/exclude` — это локальное состояние контроллера, в репозиторий оно не идёт.

Уровень тестирования: если в проекте нет `.test-ratchet.json` — `ratchet.py --root <проект> init --level <L из интервью или 3>`; он поедет в репозиторий в ветке первой задачи.

### 3. Сессии

Нужно **5 открытых сессий** Claude Code (кроме этой). Попроси пользователя:

> Открой 5 терминалов, в каждом: `cd <проект> && claude`. Для удобства переименуй их (`/rename`): coder, optimist, realist, pessimist, wiki. Режим разрешений — тот же, что у этой сессии, иначе мои сообщения будут ждать твоего ручного одобрения.

Затем `ListAgents` (загрузи `ListAgents`/`SendMessage` через ToolSearch, если нужно). Если сессии названы по ролям — сопоставь по имени, иначе предложи пользователю сопоставление через `AskUserQuestion`. Меньше пяти — не начинай, скажи, кого не хватает.

Каждой сессии отправь **онбординг** (`references/messages.md`, §1) и дождись `ready` от всех пяти. Сообщения приходят сами — не опрашивай `ListAgents` в цикле и не шли «ты готов?». Если ответа долго нет — `SendMessage` с `notify_when_idle: true` или спроси пользователя.

**Канбан-доска.** После каждого `plan.py set …` обновляй доску скилом **kanban-board**: `python3 ~/.claude/skills/kanban-board/scripts/kanban.py <план>`. В ветке задачи `KANBAN.md`/`KANBAN.html` коммитятся вместе со статусом.

Веди `.orchestrator/state.md`: какая сессия какую роль играет, текущая задача и этап, цикл исправлений, раунд дебатов. Это нужно, чтобы продолжить после сжатия контекста или перезапуска.

### 4. Конвейер одной задачи

```bash
python3 scripts/plan.py --file <план> next      # → ID, ветка, название
```

**a. Ветка и worktree.** Ветка называется по задаче (`plan.py branch <ID>`, напр. `t3-registratsiya-polzovatelya`):
```bash
git -C <проект> worktree add -b <branch> <проект>-wt/<branch> origin/<base>
python3 scripts/plan.py --file <план> set <ID> in-progress --branch <branch>
```
Отдельный worktree на задачу: основной checkout не трогается, а кодер может позже начать следующую задачу, пока идут тесты этой.

**b. Кодер.** Сообщение §2. Ждёшь `[REPORT coder <ID>] done`. Проверь: коммиты есть, полный прогон приложен, в ветке нет пуша в main.

**c. Совет тестирования.** `plan.py set <ID> testing`. Сам выполни `ratchet.py --root <worktree> status` и `guard --base origin/<base>`, разошли трём тестировщикам §3. Дальше ты — оркестратор совета по скилу **test-council**: проверка отчётов (шаг 3), консенсус (шаг 4), до **3 раундов дебатов** через сообщения §4 (шаг 5), без консенсуса — **решает человек** (`AskUserQuestion`).

**d. FAIL →** `plan.py set <ID> fixing`, сообщение кодеру §5, затем снова **c** с полным советом. Не больше **3 циклов исправлений**: после третьего FAIL остановись и спроси человека (продолжать, переформулировать задачу, отложить → `blocked`).

**e. PASS →** выполни `ratchet.py --root <worktree> update …` с цифрами финального прогона, затем сообщение кодеру §6: коммит тестов совета и храповика, `push -u origin <branch>`, MR в базовую ветку. Ждёшь ссылку на MR → `plan.py set <ID> review --mr <url>` (кодер закоммитил статус в ветке; в основном checkout обнови так же).

**f. База знаний.** Сообщение wiki §7 с отчётом по задаче (что сделано, решения, проблемы, итоги совета, ссылка на MR). Ждёшь `[REPORT wiki <ID>] done`.

**g. Отчёт пользователю** — 3–5 строк: задача, вердикт совета, ссылка на MR, что легло в БЗ. Затем `git worktree remove` не делай, пока MR не смержен (может понадобиться доработка по ревью).

### 5. Следующие задачи

- `next` вернул задачу → снова шаг 4.
- Задачи ждут зависимостей (MR не смержены) → скажи пользователю, какие MR смержить. Проверить статус: `gh pr view <url> --json state` / `glab mr view`. Смерженный → `plan.py set <ID> done`, `git worktree remove`.
- Можно вести задачи параллельно (кодер на следующей, пока совет тестирует текущую), если они независимы. Тестировщики при этом всегда работают над одной задачей за раз.
- Комментарии ревьюера в MR → сообщение кодеру в стиле §5 по той же ветке, затем совет заново.

Когда открытых задач нет — итоговый отчёт: таблица задач со статусами и MR (`plan.py list`), что осталось на ревью.

## Воркеры

Ты получил `[ORCH]`-сообщение. Отвечай только через `SendMessage` на `from` этого сообщения — твой текст в своём терминале контроллер не видит. Формат отчётов и тексты заданий — `references/messages.md`. Общие правила для всех ролей: в main не пушить; работать только в worktree из задания; если что-то мешает — `[REPORT <роль> <ID>] blocked — причина`, а не самодеятельность.

### Воркер: coder

- Реализуй задачу строго по тексту и критериям приёмки в указанном worktree. Неясность в задаче — `blocked` с вопросом, а не догадка: контроллер спросит человека.
- Покрой новое поведение общими тестами (по модулю и поведению, не по задаче).
- Коммить в ветку задачи осмысленными коммитами; пушить — только по команде финализации (§6) и только `origin <branch>`.
- **Тесты совета не трогай**: не удаляй, не ослабляй, не правь ожидания — чини код. Если уверен, что тест ошибочен, — скажи в отчёте с аргументами; решает совет или человек.

### Воркер: optimist / realist / pessimist

Загрузи скил **test-council** и работай в его **режиме одной роли**: ты — одна указанная роль, совет и дебаты ведёт контроллер. Не запускай собственных субагентов-ролей. Отчёт и ответы в дебатах — в формате test-council, с префиксом `[REPORT <роль> <ID>]`.

### Воркер: wiki

Загрузи скил **llm-wiki**. На каждое задание §7 проведи полный ingest отчёта о задаче в указанную базу: сохрани в `raw/`, страница источника, обновление связанных страниц (модули, решения, концепты проекта), index, log, `lint_wiki.py`. Если база по пути не существует — создай (`init_wiki.py`) и сообщи контроллеру.
