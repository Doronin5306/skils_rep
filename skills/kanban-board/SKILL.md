# Kanban Board

Доска — **производная от плана**: источник истины — `tasks.md` / `ROADMAP.md`, доска всегда целиком перегенерируется скриптом. Так она не расходится с планом и не создаёт конфликтов «кто прав». Статусы меняются только в плане (вручную или через `agent-orchestrator/scripts/plan.py set`), затем доска обновляется.

Скрипт: `scripts/kanban.py` (путь относительно папки скила).

## Сформировать или обновить доску

1. **Найди план.** По умолчанию скрипт ищет в текущей папке `tasks.md`, `ROADMAP.md`, `docs/tasks.md`, `docs/ROADMAP.md`. Если планов несколько или он в другом месте — передай путь явно; если неясно, какой нужен, — спроси.
2. **Проверь ручные правки.** Если `KANBAN.md` уже есть:
   ```bash
   python3 scripts/kanban.py <план> --check
   ```
   `STALE … правился вручную` при неизменённом плане значит, что кто-то двигал карточки (например, в Obsidian). Эти правки будут перезаписаны — скажи пользователю, какие карточки отличаются, и предложи перенести изменения в план. Без этого не перезаписывай.
3. **Сгенерируй:**
   ```bash
   python3 scripts/kanban.py <план> [--out-dir DIR]
   ```
   Пишет `KANBAN.md` и `KANBAN.html` рядом с планом и печатает раскладку по колонкам.
4. **Сверь раскладку с планом.** Для `tasks.md` она точная. Для `ROADMAP.md` скрипт угадывает статусы по эвристикам (ниже) — проверь, что число карточек и колонки совпадают с тем, что написано в роадмапе. Если пункты распознаны неверно, не правь доску: поправь маркеры в роадмапе (с согласия пользователя) или предложи перевести его в формат `tasks.md` — тогда статусы, зависимости и MR будут точными.
5. **Отчитайся:** раскладка по колонкам (3–7 строк), пути к файлам, `open <dir>/KANBAN.html`, чтобы посмотреть доску в браузере. Выделяй важное: что заблокировано, что ждёт зависимостей, какие MR ждут ревью.

## Как статусы попадают в колонки

**tasks.md** (формат agent-orchestrator):

| status | Колонка |
|---|---|
| todo, все `depends` выполнены | К работе |
| todo, есть невыполненные `depends` | Бэклог |
| in-progress | В работе |
| testing, fixing | Тестирование (fixing — с меткой «исправления») |
| review | Ревью (MR) |
| done | Готово |
| blocked | Заблокировано |

На карточке: ID, название, приоритет (цвет полосы в HTML), зависимости (выполненные отмечены), ветка, ссылка на MR, прогресс чек-листа критериев приёмки.

**ROADMAP.md** (свободный формат):
- Карточки — пункты верхнего уровня с чекбоксом (`- [ ]`, `- [x]`, `- [~]`/`- [/]` = в работе), а в разделах со статусным заголовком — любые пункты верхнего уровня. Вложенные чекбоксы — прогресс родительской карточки.
- Статус раздела по заголовку: Done/Готово, In progress/В работе, Testing, Review, Blocked, Planned/Next/Backlog/Планы.
- Маркеры в тексте пункта перекрывают раздел: ✅ `[done]`, 🚧 ⏳ `[WIP]` `(в работе)`, 🧪 `[testing]`, 🔍 `[review]`, ⛔ `[blocked]`.
- Заголовки без статуса — эпики (метка на карточке). Невыполненные пункты роадмапа — в «Бэклог» (готовность к работе роадмап не описывает).
- Ссылка на PR/MR в тексте пункта попадает на карточку.

## Git

Обе доски детерминированы (без даты генерации): если план не менялся, файлы не меняются, а diff показывает только реальные перемещения карточек. Коммить `KANBAN.md` и `KANBAN.html` вместе с изменением плана, которое их вызвало. При конфликте слияния в `KANBAN.*` не разрешай его руками — разреши конфликт в плане и перегенерируй доску.

`--check` подходит для CI или pre-commit: код 1, если доска устарела относительно плана.

## Вместе с agent-orchestrator

Контроллер оркестратора обновляет доску после каждого `plan.py set …` той же командой, указывая план проекта. В ветке задачи доска коммитится вместе со статусом задачи.
